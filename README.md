# 과제 12: 퀵 정렬의 피벗 선택에 따른 성능 비교

## 실행 방법
```
gcc -O2 -o quicksort_pivot quicksort_pivot.c
./quicksort_pivot
```

## 구현 요약
- 데이터: 0 ~ 999,999 범위 무작위 정수 (중복 허용), n = 1000 / 2000 / 4000 / 8000 / 16000 / 20000
- 각 n에서 같은 원본의 복사본으로 세 방법을 실행하고, 정렬 결과가 오름차순인지 검증
- 피벗 선택 함수만 다르고 분할(Partition) 알고리즘은 동일 (피벗을 맨 앞으로 옮긴 뒤 Lomuto 방식 분할)
- 비교 횟수 = 분할 중 `데이터 값 < 피벗 값` 비교 + Median-of-Three의 중앙값 결정 비교 (반복문 조건, 난수 생성, 데이터 이동은 제외)

## 측정 결과 (비교 횟수)

| n | First | Random | Median-of-Three |
|---|---:|---:|---:|
| 1,000 | 10,715 | 10,412 | 11,233 |
| 2,000 | 23,362 | 25,593 | 23,402 |
| 4,000 | 59,086 | 60,027 | 55,853 |
| 8,000 | 115,414 | 118,450 | 114,896 |
| 16,000 | 258,096 | 249,403 | 244,829 |
| 20,000 | 331,283 | 320,204 | 324,466 |

## 분석

### 1. 데이터 크기 증가에 따른 변화
세 방법 모두 n이 2배가 될 때 비교 횟수가 2배보다 조금 더 늘어납니다(예: First 8,000 → 16,000에서 약 2.24배). 이는 평균 시간복잡도 O(n log n)과 일치합니다. 무작위 데이터에서는 세 방법 모두 n log₂n 의 약 1.1~1.2배 수준(n=20,000 기준 n log₂n ≈ 285,700)으로, 이차 시간(O(n²), n=20,000이면 약 4억 회)과는 거리가 멉니다.

### 2. 피벗 방법 간 성능 차이
측정값 차이는 크지 않았고(최대 약 3~10% 이내) 일관된 순위도 없었습니다. n=1,000과 20,000에서는 Random이, n=2,000~16,000에서는 대체로 Median-of-Three가 적거나 비슷했습니다. 같은 n에서 데이터를 한 번만 생성했으므로 이 정도 차이는 데이터 배치에 따른 우연의 영향이 크고, 실험만으로 "어느 방법이 확실히 낫다"고 단정하기는 어렵습니다.

### 3. 피벗 선택이 비교 횟수에 영향을 주는 이유
- 한 번의 분할은 구간 길이 m에 대해 m−1번 비교하므로, 총 비교 횟수는 분할 트리의 깊이와 균형에 의해 결정됩니다. 피벗이 구간의 중앙값에 가까울수록 두 부분이 균등해져 깊이가 약 log₂n이 되고, 치우칠수록 깊이가 커집니다.
- **First**: 입력이 무작위면 첫 원소도 무작위 원소와 통계적으로 같아 평균 성능이 좋습니다. 그러나 이미 정렬된(또는 역순) 입력에서는 매번 최솟값/최댓값이 피벗이 되어 분할이 0 : m−1로 치우쳐 O(n²)이 됩니다. 이번 데이터는 무작위라 이 약점이 드러나지 않았습니다.
- **Random**: 입력 순서와 무관하게 평균적으로 좋은 분할을 기대할 수 있어 특정 입력에 의한 최악의 경우를 피합니다. 다만 무작위 데이터에서는 First보다 나아질 이유가 없어 결과가 비슷하게 나왔습니다. 난수 생성 비용은 비교 횟수에는 포함되지 않지만 실제 시간에는 부담이 됩니다.
- **Median-of-Three**: 세 값의 중앙값은 극단값일 확률이 낮아 분할이 더 균형 잡히며, 이론적으로 비교 횟수가 평균 약 14% 줄어듭니다(2n ln n → 약 1.71n ln n). 반면 피벗을 정하는 데 분할마다 2~3번의 비교가 추가됩니다. 작은 구간에서는 이 추가 비용이 이득을 상쇄할 수 있고, n=1,000에서 Median-of-Three가 가장 많이 나온 이유로 볼 수 있습니다. n이 커질수록 균형 개선의 이득이 커져 대체로 유리해졌습니다.

### 4. 효과적이었던 방법
이번 무작위 데이터 기준으로는 n이 큰 구간(4,000 이상)에서 Median-of-Three가 4번 중 3번(4,000, 8,000, 16,000) 가장 적었고, 20,000에서는 Random이 약간 적었습니다. 따라서 큰 데이터에서 Median-of-Three가 약간 유리한 경향은 있으나 차이가 작아, 이 실험의 결론으로는 "무작위 데이터에서는 세 방법이 비슷하다"가 더 정확합니다. 정렬되어 있거나 거의 정렬된 데이터가 들어올 가능성까지 고려하면 First는 위험하고, Random이나 Median-of-Three가 안전한 선택입니다. (더 확실한 결론을 위해서는 같은 n에서 여러 번 반복해 평균을 내거나, 정렬된 입력을 추가로 실험해야 합니다.)

## [보너스] 재귀적 vs 반복적 퀵 정렬 실행시간

조건: n = 10,000, 피벗 = Median-of-Three, 동일한 원본 데이터와 분할 알고리즘 사용, 배열 복사·정렬 검증은 시간 측정에서 제외, 1,000회 반복 후 평균 (`-O2`).

실행 3회 결과:

| 실행 | Recursive | Iterative |
|---|---:|---:|
| 1 | 0.6709 ms | 0.6736 ms |
| 2 | 0.6727 ms | 0.6751 ms |
| 3 | 0.6452 ms | 0.6506 ms |

### 분석
두 방법의 실행시간은 거의 같았고, 반복적 방법이 0.3~0.8% 정도 미세하게 느렸습니다. 이 정도 차이는 측정 오차 범위에 가깝습니다.

- 두 구현은 동일한 분할과 동일한 구간 순서(왼쪽 → 오른쪽)로 처리하므로 비교·교환 횟수가 같고, 시간의 대부분은 분할 연산이 차지합니다.
- 재귀 호출 오버헤드(함수 호출, 스택 프레임 생성)와 반복 방식의 스택 push/pop 비용은 모두 분할 한 번에 비해 매우 작으며, 최적화(-O2)로 더 줄어듭니다.
- 반복적 방법은 스택 배열을 직접 관리하기 위해 `malloc`과 push/pop 연산이 추가되고, 컴파일러가 최적화하기 어려운 메모리 접근이 있어 아주 조금 느려진 것으로 보입니다.
- 실행시간 차이보다는 안정성 면에서 차이가 있습니다. 재귀 방식은 입력이 최악(치우친 분할)일 때 호출 깊이가 O(n)이 되어 스택 오버플로 위험이 있고, 반복 방식은 힙의 스택 배열을 쓰므로 이 위험을 피할 수 있습니다(더 큰 구간을 스택에 먼저 넣고 작은 구간부터 처리하면 스택 깊이를 O(log n)으로 제한할 수도 있습니다).
